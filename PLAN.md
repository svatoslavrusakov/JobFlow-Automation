# План разработки Auto_hh

Последнее обновление: 2026-11-15.

Этот файл хранит порядок работ, состояние пунктов и историю решений.

## Как ведём план

- Используем единую нумерацию от 1. Перенумерацию выполняем только
  по прямой просьбе пользователя и записываем соответствие номеров в журнал.
- Новые пункты добавляем в конец со следующим свободным номером,
  если пользователь явно не указал другое место вставки.
- После выполнения или изменения пункта обновляем его строку.
- Выполненные, отложенные и исключённые пункты не удаляем.
- Изменение статуса или очередности записываем в журнал решений.
- Для исключённого пункта указываем причину и этап либо коммит,
  на котором приняли решение.
- Если коммит ещё не создан, пишем «Ожидает коммита».
  Хэш добавляем при следующем обновлении плана.
- Сначала показываем предлагаемое изменение пользователю,
  затем применяем после согласования.

## Статусы

- Запланирован — работа ещё не начата.
- В работе — согласованное изменение внедряется.
- Частично реализован — выполнена часть пункта; оставшаяся работа указана в его строке.
- На проверке — изменение внесено, оговорённая проверка ещё не завершена.
- Выполнен — результат получен и оговорённая проверка пройдена.
- Отложен — сейчас не выполняем, пункт остаётся в плане.
- Исключён — решили отказаться; причина сохраняется в журнале.

Наличие коммита само по себе не означает, что проверка пройдена.

## Обработка ссылок из таблицы — пункт 12

Пользователь добавляет интересующие вакансии в колонку «Ссылка».
Остальные данные программа получает со страниц hh через Selenium.

Порядок работы:

1. Открыть выбранный лист и найти колонки по заголовкам.
2. Выбрать строки с заполненной «Ссылка» и пустым «Статус».
   Строки со статусами `new`, `done`, `wait`, `thinking`, `no`,
   `reject` и `form` автоматически повторно не обрабатывать.
3. Получить ID из ссылки, очистить ссылку и открыть вакансию.
   Название читать со страницы: в этом сценарии карточки поиска нет.
4. Использовать общие функции `hh/vacancy_reader.py` для чтения данных.
   Сначала доступны ID, заголовок, описание, ссылка, компания,
   ссылка на компанию и зарплата. Новые функции сбора данных
   должны затем использоваться обоими сценариями.
5. Заполнить доступные данные в исходной строке.
   Новую строку для той же вакансии не добавлять.
   Ручные значения, комментарии, сопроводительные и результаты ИИ
   сохранять; по умолчанию дополнять пустые ячейки.
6. После успешного сбора обязательных данных установить `new`.
   При ошибке сообщить о ней, оставить строку доступной для повторной
   попытки и продолжить остальные ссылки.

Проверку дублей выполнять с учётом исходной строки: её собственный ID
не должен мешать дополнению этой строки. Совпадение ID в другой строке
нужно показать пользователю и не создавать ещё одну запись.

Поисковый чёрный список не применять к вручную выбранным ссылкам:
для этого режима действуют условия отбора строк, указанные выше.
Отправка откликов и генерация писем выполняются отдельными этапами.
Дата и время добавления ставятся при сохранении данных вакансии, но не при импорте одной ссылки.

Запуск: `Scripts/run.py search` для поиска, `Scripts/run.py fill` для ссылок.
Оба сценария используют общие `hh/vacancy_reader.py`, `tables/sheets.py`,
`tables/duplicates.py`, `core/utils.py` и `core/config.py`. Код проверен пользователем.
В начале запуска читаем заголовки и одним запросом колонки ID, Ссылка, Статус.
Остальные данные читаются только из обрабатываемой строки перед записью.
Три колонки пока целиком находятся в памяти; чтение порциями — отдельное улучшение.
Дубли проверяются по этому снимку выбранного листа;
режим рассчитан на одного обработчика. Конфликтующие строки пропускаются все,
чтобы пользователь выбрал нужную. Сортировку строк выполняем между запусками.

Режимы hh сохраняются. Номера существующих пунктов не меняем.

- **Пункт 18.** Реализован `workflows/collect_html.py` и команда `run.py collect-html`: чтение ссылок с пустым статусом, открытие в Chrome и сохранение текущего DOM.
   В `source.json` записываются версия, ключ SHA-256 полного URL, исходный и конечный адреса, локальное время и хеш HTML. Снимок публикуется после сохранения обоих файлов.
   Готовые снимки проверяются и пропускаются до Chrome; повреждённые не перезаписываются. Ручная проверка ожидается.
- **Пункт 19.** После ручного включения прокси запустить `run.py process-html`.
   ИИ распознаёт заголовок, компанию, описание, зарплату, контакты и ссылку
   на анкету. Селекторы этих полей для каждого сайта заранее не задаём.
   Ответ проверяем и сохраняем в `vacancy.json`; неизвестные значения
   остаются пустыми строками. Формат полей общий с hh: `core/vacancy.py`.
   Строковый ID внешней вакансии — `site:<ключ URL>`; адрес сохраняется полностью.
   Готовые JSON пропускаются, повреждённые не перезаписываются; лимит и паузы общие с ИИ.
- **Пункт 15.** Реализован `run.py draft-html`: общая с hh генерация письма, рисков,
   оценки и специальных требований по `vacancy.json` и резюме. Результат — `draft.json`;
   готовые документы пропускаются, исходники сверяются перед записью. Лимит и паузы общие
   с распознаванием HTML. Адаптация резюме внешних вакансий ещё не реализована.
   Оригинал резюме не перезаписываем.
- **Пункт 20.** После ручного выключения прокси запустить `run.py import-results`:
   готовые файлы проверяются и добавляются в отдельный выбранный лист. Общий импорт партиями
   используется также HTML-импортом hh; существующие ID и полные URL пропускаются.
   Ключ и источник внешней вакансии проверяем отдельно от числового ID hh.
   Успешная обработка ИИ и сохранённое письмо дают `done`; `wait` — только после подтверждённой
   отправки, сначала вручную. Автоматический отправщик остаётся пунктом 16.

Правила обмена и повторного запуска:

- В отдельной папке вакансии храним `source.json`, исходный `page.html`,
  проверенный `vacancy.json` и `draft.json`.
  Форматы вакансии и ответа ИИ общие с hh. Импорт реализован в пункте 20 и ожидает ручной проверки Google.
- Этапы запускаются независимо, в том числе на разных ПК.
  Google Таблица хранит очередь и результаты; сохранённые HTML и JSON
  при переносе между ПК передаются отдельно.
- Прокси переключает пользователь вручную между этапами.
- Сохраняем текущий `driver.page_source` после пауз и прокрутки. Отдельные iframe,
  shadow DOM и незагруженные части страницы требуют отдельной проверки.
  Для ИИ можно подготовить облегчённую копию,
  сохраняя тексты, структуру, ссылки и данные вакансии, включая JobPosting.
  Слишком длинные документы обрабатываем частями, сохраняя контекст вакансии.
- Текст страницы считаем данными, а не командами для ИИ.
  Подводные камни обосновываем содержимым вакансии, факты резюме не выдумываем.
- Готовый результат повторно не генерируем без явного запроса.
  Перед импортом проверяем ключ/ссылку, чтобы не создавать дубли.
- Значимые параметры и фрагменты корпоративных URL сохраняем:
  они могут определять вакансию. Очистку ссылок hh сюда не переносим.

Ближайшая проверка — реальный прогон нового подтверждения отправки (13, 16):
одна загрузка вакансии, один финальный клик, ожидание результата на текущей странице.
Окно города не должно давать form; неизвестный результат останавливает запуск.
Код применён и проверен локально. Обработку капчи оставляем прежней по решению пользователя.
Далее — проверка ИИ-этапа (15), распознавание сохранённых HTML (19) и импорт результатов (20).
Проверки оставшихся ветвей 8, 17, 18 и даты добавления из пункта 6 ведём отдельно.
Ожидания в сборщиках (5) остаются отложенными.

## Ключевые слова и резюме — пункты 32–34

- **Пункт 32.** Для каждого ID модель извлекает только ключевые слова конкретной вакансии.
  Общий список не подставляется в её строку; обработка не зависит от его наличия. Программа
  приводит названия к единому виду и записывает список через `;` в колонку «Ключевые слова».
  Например: `Python`, `pyhton`, `Пайтон` → `Python`. Повторы в одной ячейке удаляются.
- Обрабатываются строки со ссылкой, описанием и пустыми ключевыми словами, независимо от статуса.
  При отсутствии компетенций ставится `—`; для повторного анализа нужно очистить ячейку.
  Статусы и остальные поля сохраняются. Счётчики, хеширование и служебные листы исключены:
  пользователь самостоятельно строит аналитику в Google Таблице.
  Подробности: [Docs/competencies.md](Docs/competencies.md).
- **Пункт 33.** Сопоставляем собственный список выбранной вакансии с исходным резюме и заполняем
  готовый пользовательский шаблон, сохраняя его структуру и оформление. Используем
  существующие ИИ-запросы и подготовку документов из пунктов 15 и 23.
  Ключевые слова встраиваем в подходящие навыки и описание опыта с опорой на исходные факты;
  неподтверждённые требования оставляем вопросами для ручного решения.
  Сохраняем отдельный вариант для конкретной вакансии; исходное резюме и шаблон сохраняются.
  Перед использованием результата нужна ручная проверка; автоматическая отправка — отдельный этап.

- **Пункт 34.** Общий список ключевых слов нужен для других целей и ведётся отдельной задачей.
  Ранее обсуждённые сопоставление существующих терминов и добавление новых относятся к этому списку.
  Его назначение, формат хранения и сценарий работы с ИИ определим перед реализацией;
  не связываем его готовность с извлечением слов для каждой вакансии.

## Общие договорённости

- Код остаётся небольшим и понятным: функции, ясные имена,
  короткие комментарии и актуальная документация.
- Сохраняем совместимость с Python 3.11 на старом компьютере.
- Прежние сценарии hh работают через Selenium. Новый экранный отправщик — отдельный пункт 28, без замены старых команд.
- Сборщик, генератор и отправщик должны запускаться независимо,
  в том числе на разных компьютерах.
- Общее хранилище компонентов — Google Таблица.
- Колонки определяются по назначению заголовка, а не по буквам. При переименовании через окно назначение сохраняется в примечании Google.
- Актуальные названия и порядок колонок приведены в разделе «Колонки Google Таблицы».
- Зарплата сохраняется как на сайте, контакты HR — только если они указаны и доступны.
- Дата и время добавления вакансии не являются подтверждением отправки отклика.
- `new` — данные вакансии собраны, ожидается обработка ИИ; отправка запрещена.
- `done` — обработка ИИ завершена, готовое сопроводительное сохранено; отклик ещё не отправлен.
- Отправщик выбирает только `done`. Пустой статус и `new` не допускают отправку даже при заполненном письме.
- Перед отправкой промежуточный статус не ставим. Перезапуск `done` начинается с проверки готовности строки, затем состояния hh.
- `wait` — отклик отправлен, ответа пока нет.
- `thinking` — пользователь обдумывает вакансию либо ИИ нашёл специальные требования к отклику. Причина хранится в «Требования к отклику»; после проверки пользователь может поставить done.
- `no` — пользователь исключил вакансию.
- `reject` — получен отказ работодателя.
- `invite` — получено приглашение работодателя.
- `archive` — вакансия архивная, нового ответа не показано; повторно не проверяем.
- `unavailable` — недоступна этому аккаунту, требуется ручная проверка; автоматически не повторяем.
- Сообщение «Вам недоступна эта вакансия» не останавливает очередь, даже при форме внутри блока.
- Явные reject/invite сохраняем и на архивных страницах.
- «Дата проверки» обновляется после распознавания страницы, даже при прежнем wait.
- Отбор по дате отправки отклика отложен по просьбе пользователя.
- `form` — требуется ручное заполнение анкеты.
